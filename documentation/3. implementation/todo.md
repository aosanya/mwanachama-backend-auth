| DEV-1698 | 🐞 **BUG — `OperatorAttempt.Fail`/`PhoneAttempt.Fail` never reset a sub-threshold failure count on a fresh window, only when an actual lock has expired.** `models/operator.go`'s `OperatorAttempt.Fail` and `models/auth.go`'s `PhoneAttempt.Fail` (identical shape in both) only zero `Failed` when `!a.LockedUntil.IsZero() && !now.Before(a.LockedUntil)` — i.e. only after a lock was actually *triggered* (crossing the 5-failure threshold) and has since expired. Demonstrated live against the real `OperatorStore.RecordFailure` (sqlite, in-process, the same method `routes/operator.go`'s `OperatorSignIn` calls on every failed console sign-in): 3 failures on 2026-01-01, then one more failure exactly a year later (2027-01-01) — `next.Failed == 4`, not `1`, even though a full year separates them. | DEV-1698 | 🐞 **BUG — a failed-sign-in counter that never reaches the lock threshold never resets on its own; widely-spaced failures accumulate for the address/number's whole lifetime instead of resetting per window, contradicting this package's own documented intent.** `models.OperatorAttempt.Fail` (`models/operator.go:154`) and `models.PhoneAttempt.Fail` (`models/auth.go:193`) — identical shape — only reset `Failed` to 0 when the address/number was ALREADY locked (`LockedUntil` set) *and* that lock has since expired (`!now.Before(a.LockedUntil)`). An address/number that fails fewer than `OperatorLockAfter`/`AuthLockAfter` (5) times never gets `LockedUntil` set at all, so those failures are never reset by elapsed time — they simply accumulate until a 5th-ever failure locks it, however far apart in time the failures actually were. This directly contradicts the method's own doc comment: "A lock that has already expired resets the count first, so the five are always consecutive within one window rather than cumulative over an address's lifetime — otherwise a credential used for a year would lock on its fifth typo ever." Demonstrated directly against `OperatorAttempt.Fail` (a controllable clock is needed; `OperatorSignIn`'s HTTP handler hardcodes `time.Now()` and cannot be driven this way): four wrong-password failures for one address, one per calendar year (2020-01-01, 2021-01-01, 2022-01-01, 2023-01-01) — `Failed` climbs 1→2→3→4, never locked — then a 5th failure a year later (2024-01-01) locks the address (`Failed=5 Locked=true LockedUntil=2024-01-01T00:15:00Z`) — exactly the "a credential used for a year locks on its fifth typo ever" scenario the doc comment says cannot happen. `PhoneAttempt.Fail` reproduces byte-for-byte identically (same test shape, see pinning tests below). Separately confirmed this does **not** create an enumeration asymmetry: a no-credential address's `OperatorSignIn` attempts count and lock identically to a real credential's wrong-password attempts — status code, `tries_left` and the refusal sentence are byte-for-byte the same at every step of a full lock-out cycle driven through the real HTTP surface (`httptest.NewServer` + real `http.Client` over `routes.OperatorSignInRoutes`) — so the anti-enumeration property this repo's and the gateway's CLAUDE.md both call out by name holds; this is a pure reset-policy correctness gap, not an enumeration hole. Affects both the operator console door (reachable today via `POST /operator/signin`) and, identically, the member phone sign-in door once the gateway wires `phoneChallenge`/`phoneVerify` against `AuthStore.RecordPhoneFailure` (that route stays gateway-side per `routes/doc.go` and is not reachable through this repo's own `routes/` package today). **Fix location**: `models/operator.go`'s `OperatorAttempt.Fail` and `models/auth.go`'s `PhoneAttempt.Fail` — needs an explicit policy call (not made here): either reset the count once enough time has passed since the *last* failure regardless of whether the address/number ever actually got locked, or correct the doc comment to describe the real, apparently-intentional "N wrong guesses ever, absent a full lock-and-wait cycle" policy instead. | 📋 | — |
