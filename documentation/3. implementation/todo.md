| DEV-1700 | 🐞 **BUG — `ConsumeChallenge` runs, and permanently marks the challenge used, before `DeviceVerify`/`RecoveryVerify` actually check the proof — so a single wrong signature or wrong secret burns the challenge forever, whether or not the guesser was the legitimate holder.** `routes/device.go`'s `DeviceVerify` calls `auth.ConsumeChallenge(ctx, in.ChallengeID, now)` (line 98) *before* `mwanachamaauth.VerifyDeviceProof` (line 115); `routes/recovery.go`'s `RecoveryVerify` calls the same `ConsumeChallenge` (line 73) *before* comparing `c.Secret != in.Secret` (line 78) — identical ordering bug, same root cause, both call sites. `ConsumeChallenge` itself (`challenge_impl.go`) only checks that the challenge exists, is unconsumed, and is unexpired — it has no idea whether the proof that follows will turn out to be right. Demonstrated end-to-end over the real handlers (not the store directly): register a device, create a device challenge, `POST /devices/{id}/verify` once with a garbage signature (`401 device proof invalid`, as expected) — then `POST` again with the device's **real**, correctly Ed25519-signed proof against the **same** `challenge_id`: `401 {"error":"auth: not found"}`, zero sessions minted. Byte-for-byte the same shape for recovery: `POST /recovery/verify` with a wrong guess (`401 secret mismatch`), then the member's own correct secret against the same challenge: `401 {"error":"auth: not found"}`. **This is a real availability/security hole, not just a UX papercut**, because both `deviceID` and `challenge_id` mint as sequential, predictable strings in production Postgres (`gormstore/tables.go`'s `mintID`: `SELECT nextval('auth_device_seq'/'auth_challenge_seq')` → `"device-<n>"`/`"chal-<n>"`, confirmed by reading `gormstore/device.go`/`challenge.go`'s `BeforeCreate`; only the sqlite test dialect falls back to a UUID suffix). Neither `DeviceVerify` nor `RecoveryVerify` requires any credential to reach `ConsumeChallenge` — `DeviceVerify` is deliberately public "by necessity" (its own DEV-1217 doc comment) since proving a device is how a session is first obtained. Put together: an attacker with zero credentials can enumerate `device-1, device-2, …` and `chal-1, chal-2, …` and POST one garbage verify/recovery request per id, permanently denying every in-flight device sign-in and account-recovery attempt fleet-wide — no cryptographic effort, no interception, no rate limit encountered (each guess is its own, valid-shaped, one-shot request). **Fix location**: `routes/device.go`'s `DeviceVerify` and `routes/recovery.go`'s `RecoveryVerify` — check the proof (signature/secret) against the challenge's stored secret *before* calling `ConsumeChallenge`, and only consume on success; a separate, explicit rate-limit/lockout on repeated wrong guesses against one challenge (mirroring `PhoneAttempt`/`OperatorAttempt`'s existing counter shape) is the right place to bound retries, not an implicit single-shot burn shared with the ordering-error path. Predictable sequential ids compound this but are not this row's own fix target — flagging them here as the reason severity is "fleet-wide DoS," not filing a second row, since changing the id scheme is a much larger, separately-decidable change (see `mwanachama-backend-comm/CLAUDE.md`'s own "ids are still human-readable and prefix-numbered ... by design" precedent for why that tradeoff was made deliberately elsewhere in this fleet and may be here too). | 📋 | — |
| DEV-1698 | 🐞 **BUG — a failed-sign-in counter that never reaches the lock threshold never resets on its own; widely-spaced failures accumulate for the address/number's whole lifetime instead of resetting per window, contradicting this package's own documented intent.** `models.OperatorAttempt.Fail` (`models/operator.go:154`) and `models.PhoneAttempt.Fail` (`models/auth.go:193`) — identical shape — only reset `Failed` to 0 when the address/number was ALREADY locked (`LockedUntil` set) *and* that lock has since expired (`!now.Before(a.LockedUntil)`). An address/number that fails fewer than `OperatorLockAfter`/`AuthLockAfter` (5) times never gets `LockedUntil` set at all, so those failures are never reset by elapsed time — they simply accumulate until a 5th-ever failure locks it, however far apart in time the failures actually were. This directly contradicts the method's own doc comment: "A lock that has already expired resets the count first, so the five are always consecutive within one window rather than cumulative over an address's lifetime — otherwise a credential used for a year would lock on its fifth typo ever." Demonstrated directly against `OperatorAttempt.Fail` (a controllable clock is needed; `OperatorSignIn`'s HTTP handler hardcodes `time.Now()` and cannot be driven this way): four wrong-password failures for one address, one per calendar year (2020-01-01, 2021-01-01, 2022-01-01, 2023-01-01) — `Failed` climbs 1→2→3→4, never locked — then a 5th failure a year later (2024-01-01) locks the address (`Failed=5 Locked=true LockedUntil=2024-01-01T00:15:00Z`) — exactly the "a credential used for a year locks on its fifth typo ever" scenario the doc comment says cannot happen. `PhoneAttempt.Fail` reproduces byte-for-byte identically (same test shape, see pinning tests below). Separately confirmed this does **not** create an enumeration asymmetry: a no-credential address's `OperatorSignIn` attempts count and lock identically to a real credential's wrong-password attempts — status code, `tries_left` and the refusal sentence are byte-for-byte the same at every step of a full lock-out cycle driven through the real HTTP surface (`httptest.NewServer` + real `http.Client` over `routes.OperatorSignInRoutes`) — so the anti-enumeration property this repo's and the gateway's CLAUDE.md both call out by name holds; this is a pure reset-policy correctness gap, not an enumeration hole. Affects both the operator console door (reachable today via `POST /operator/signin`) and, identically, the member phone sign-in door once the gateway wires `phoneChallenge`/`phoneVerify` against `AuthStore.RecordPhoneFailure` (that route stays gateway-side per `routes/doc.go` and is not reachable through this repo's own `routes/` package today). **Fix location**: `models/operator.go`'s `OperatorAttempt.Fail` and `models/auth.go`'s `PhoneAttempt.Fail` — needs an explicit policy call (not made here): either reset the count once enough time has passed since the *last* failure regardless of whether the address/number ever actually got locked, or correct the doc comment to describe the real, apparently-intentional "N wrong guesses ever, absent a full lock-and-wait cycle" policy instead. | 📋 | — |
