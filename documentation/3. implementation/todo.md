| DEV-1705 | ⏸️ **DECISION — two carriers hold a secret the models type deliberately does not, and the standard wants it on the model instead.** `store.go`'s `credentialRecord` holds `password_hash` and `saltRecord` holds the raw salt `secret`; `models.OperatorCredential` and `models.Salt` have neither. The declared-domain standard's own answer for a stored secret is to put it on the model with a `json:"-"` tag, the way `mwanachama-backend-catalog` carries `ShareLink.KeyHash` — one carrier per role, no conversion function. **The reason this repo did not do that**: `KeyHash` is a SHA-256 *hash*, and `Salt.Secret` is **live key material**, the one value in the module that is a key rather than a record of one. This repo's `CLAUDE.md` has always called the absence of a secret field on `models.Salt` a load-bearing security property, and the standardize skill is explicit that where a repo's own CLAUDE.md forbids something the standard wants, the conflict is surfaced for the owner rather than resolved by editing the CLAUDE.md. **The options**: (a) keep the two unexported carriers, which costs one conversion function each and keeps the raw key off any type an API response is built from — what is in place today; (b) move both fields onto the models types with `json:"-"`, matching catalog exactly, accepting that a `%+v` of a `Salt` then prints key material; (c) keep (a) for `salt` and take (b) for `credential`, on the grounds that a password hash is a hash. Nothing is blocked either way. | ⏸️ | owner |
| DEV-1704 | 📋 **Nothing validates that a stored password hash is actually an argon2id digest, and declaring that it must be is a behaviour change rather than a moved rule.** An `argon2id_digest` pattern on `credential.password_hash` was written during DEV-1703 and removed again: it turned `TestOperatorCreateAndVerifier`, `TestOperatorDisableIsIdempotentAndKeepsFirstStamp` and `TestOperatorListForMemberIncludesDisabled` red, because those tests pass `"hash-1"`. That is the evidence that the refusal is new — the store has never checked, so a caller handing it anything has always succeeded. `password.go`'s `Hash` is the only producer in this repo and always emits PHC `$argon2id$...`, so the pattern would hold for every real caller; the question is whether a store should refuse a verifier it cannot parse, which would catch a mount that wired a plaintext password into `Create` by mistake. **Decide, then either declare the pattern and fix the three tests, or write down that the store deliberately does not care.** The declaration is one line in `auth.blueprint.json` plus one entry in `patterns.go`. | 📋 | — |
| DEV-1706 | 📋 **Four of the ten declared addresses are single calls and could be dispatched rather than handled, once there is one manager to dispatch against.** `auth.operator_credential.list`, `auth.operator_credential.disable`, `auth.verification.set` and `auth.phone_salt.list` are each a decode-call-encode over one repository method, so `dispatch.Dispatch` could build them and they would gain argument binding, the declared `returns`, and an MCP tool each for free. **What stops it is not the addresses, it is the shape**: `dispatch.Deps` takes one `Manager`, and these four live on `OperatorRepository`, `VerificationRepository` and `PhoneSaltRepository`. | DEV-1701 | 🐞 **BUG — `ConsumeChallenge` runs, and permanently marks the challenge used, before `DeviceVerify`/`RecoveryVerify` actually check the proof — so a single wrong signature or wrong secret burns the challenge forever, whether or not the guesser was the legitimate holder.** `routes/device.go`'s `DeviceVerify` calls `auth.ConsumeChallenge(ctx, in.ChallengeID, now)` (line 98) *before* `mwanachamaauth.VerifyDeviceProof` (line 115); `routes/recovery.go`'s `RecoveryVerify` calls the same `ConsumeChallenge` (line 73) *before* comparing `c.Secret != in.Secret` (line 78) — identical ordering bug, same root cause, both call sites. `ConsumeChallenge` itself (`challenge_impl.go`) only checks that the challenge exists, is unconsumed, and is unexpired — it has no idea whether the proof that follows will turn out to be right. Demonstrated end-to-end over the real handlers (not the store directly): register a device, create a device challenge, `POST /devices/{id}/verify` once with a garbage signature (`401 device proof invalid`, as expected) — then `POST` again with the device's **real**, correctly Ed25519-signed proof against the **same** `challenge_id`: `401 {"error":"auth: not found"}`, zero sessions minted. Byte-for-byte the same shape for recovery: `POST /recovery/verify` with a wrong guess (`401 secret mismatch`), then the member's own correct secret against the same challenge: `401 {"error":"auth: not found"}`. **This is a real availability/security hole, not just a UX papercut**, because both `deviceID` and `challenge_id` mint as sequential, predictable strings in production Postgres (`gormstore/tables.go`'s `mintID`: `SELECT nextval('auth_device_seq'/'auth_challenge_seq')` → `"device-<n>"`/`"chal-<n>"`, confirmed by reading `gormstore/device.go`/`challenge.go`'s `BeforeCreate`; only the sqlite test dialect falls back to a UUID suffix). Neither `DeviceVerify` nor `RecoveryVerify` requires any credential to reach `ConsumeChallenge` — `DeviceVerify` is deliberately public "by necessity" (its own DEV-1217 doc comment) since proving a device is how a session is first obtained. Put together: an attacker with zero credentials can enumerate `device-1, device-2, …` and `chal-1, chal-2, …` and POST one garbage verify/recovery request per id, permanently denying every in-flight device sign-in and account-recovery attempt fleet-wide — no cryptographic effort, no interception, no rate limit encountered (each guess is its own, valid-shaped, one-shot request). **Fix location**: `routes/device.go`'s `DeviceVerify` and `routes/recovery.go`'s `RecoveryVerify` — check the proof (signature/secret) against the challenge's stored secret *before* calling `ConsumeChallenge`, and only consume on success; a separate, explicit rate-limit/lockout on repeated wrong guesses against one challenge (mirroring `PhoneAttempt`/`OperatorAttempt`'s existing counter shape) is the right place to bound retries, not an implicit single-shot burn shared with the ordering-error path. Predictable sequential ids compound this but are not this row's own fix target — flagging them here as the reason severity is "fleet-wide DoS," not filing a second row, since changing the id scheme is a much larger, separately-decidable change (see `mwanachama-backend-comm/CLAUDE.md`'s own "ids are still human-readable and prefix-numbered ... by design" precedent for why that tradeoff was made deliberately elsewhere in this fleet and may be here too). | 📋 | — |
| DEV-1700 | 🔑 **Own the role→action grant table — a sixth domain in this repo.** This repo is identity only today: challenges, devices, operators, phone proof, passwords. There is no `Role`, `Capability` or `Permission` type anywhere in it, so nothing in the platform can answer "may this subject do this?" — every `routes/` package across the org leaves the gate to whatever mounts it, and no mounting process implements one. Decided 2026-09-23 that this repo owns the mapping, so there is one answer for every module rather than a grant table per backend; a module declares what acts exist and stays ignorant of who holds them. The act vocabulary comes from the route spec as stable `action` ids — `<module>.<resource>.<verb>`, e.g. `catalog.entry.open`, `catalog.share_link.issue` — which are stable across domains (an agency storefront and a library both emit `catalog.entry.open`) and across path changes, so a grant survives a refactor. This is what `mwanachama-backend-agency`'s seat configs already ask for and cannot supply: the `unenforceable` block in the Wakala agency's `actor.json` reads *"capabilities — needed: a map from these names to the real gates before any of this is claimed to be enforced."* **Unresolved and part of this work:** whether this repo's roles *are* `mwanachama-backend-agency`'s `Role.Code` values (R-1, R-2, …) by code, or a separate vocabulary the agency document maps onto; and how a grant is scoped — this agency, this library, or every instance — since an action says what but not where. Design: [architecture-spec-driven-modules.md](../../../developer/documentation/2.%20design/architecture-spec-driven-modules.md) §5, register entry 2026-09-23. | 📋 | the route spec's `action` ids (W14 on `mwanachama-website`'s board) |
| DEV-1698 | 🐞 **BUG — a failed-sign-in counter that never reaches the lock threshold never resets on its own; widely-spaced failures accumulate for the address/number's whole lifetime instead of resetting per window, contradicting this package's own documented intent.** `models.OperatorAttempt.Fail` (`models/operator.go:154`) and `models.PhoneAttempt.Fail` (`models/auth.go:193`) — identical shape — only reset `Failed` to 0 when the address/number was ALREADY locked (`LockedUntil` set) *and* that lock has since expired (`!now.Before(a.LockedUntil)`). An address/number that fails fewer than `OperatorLockAfter`/`AuthLockAfter` (5) times never gets `LockedUntil` set at all, so those failures are never reset by elapsed time — they simply accumulate until a 5th-ever failure locks it, however far apart in time the failures actually were. This directly contradicts the method's own doc comment: "A lock that has already expired resets the count first, so the five are always consecutive within one window rather than cumulative over an address's lifetime — otherwise a credential used for a year would lock on its fifth typo ever." Demonstrated directly against `OperatorAttempt.Fail` (a controllable clock is needed; `OperatorSignIn`'s HTTP handler hardcodes `time.Now()` and cannot be driven this way): four wrong-password failures for one address, one per calendar year (2020-01-01, 2021-01-01, 2022-01-01, 2023-01-01) — `Failed` climbs 1→2→3→4, never locked — then a 5th failure a year later (2024-01-01) locks the address (`Failed=5 Locked=true LockedUntil=2024-01-01T00:15:00Z`) — exactly the "a credential used for a year locks on its fifth typo ever" scenario the doc comment says cannot happen. `PhoneAttempt.Fail` reproduces byte-for-byte identically (same test shape, see pinning tests below). Separately confirmed this does **not** create an enumeration asymmetry: a no-credential address's `OperatorSignIn` attempts count and lock identically to a real credential's wrong-password attempts — status code, `tries_left` and the refusal sentence are byte-for-byte the same at every step of a full lock-out cycle driven through the real HTTP surface (`httptest.NewServer` + real `http.Client` over `routes.OperatorSignInRoutes`) — so the anti-enumeration property this repo's and the gateway's CLAUDE.md both call out by name holds; this is a pure reset-policy correctness gap, not an enumeration hole. Affects both the operator console door (reachable today via `POST /operator/signin`) and, identically, the member phone sign-in door once the gateway wires `phoneChallenge`/`phoneVerify` against `AuthStore.RecordPhoneFailure` (that route stays gateway-side per `routes/doc.go` and is not reachable through this repo's own `routes/` package today). **Fix location**: `models/operator.go`'s `OperatorAttempt.Fail` and `models/auth.go`'s `PhoneAttempt.Fail` — needs an explicit policy call (not made here): either reset the count once enough time has passed since the *last* failure regardless of whether the address/number ever actually got locked, or correct the doc comment to describe the real, apparently-intentional "N wrong guesses ever, absent a full lock-and-wait cycle" policy instead. | 📋 | — |
