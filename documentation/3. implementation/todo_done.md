| DEV-1707 | The "absent" predicate asks the database for the column's type, so an adopted `timestamptz` stops breaking four sites | 2026-10-01 | `mwanachama-wakala-api` would not boot: `could not provision mwanachama-backend-auth tables`. Two causes, the second the interesting one. **The provisioning half** was in shared (S50 there): `DropIndexes` matched `auth_challenge_pkey` off this repo's `auth_` prefix and Postgres refuses to drop an index its own primary-key constraint requires. **This repo's half**: `unsetText` was a constant `(c IS NULL OR c = '')`, and the `= ''` arm is invalid SQL against a `timestamptz` — `invalid input syntax for type timestamp with time zone: ""`. That is exactly what adoption leaves behind: `spec.Migrate` is `create table if not exists`, so the eight tables renamed in from the retired api-gateway keep **the gateway's** column types, and `signed_out_at`, `disabled_at` and `retired_at` are all real `timestamptz` there while `auth.blueprint.json` declares `timestamp`, which `spec.Migrate` emits as `text`. **Four sites were broken against the live database** — the one-live-salt index in `Provision`, `PhoneSaltStore.Retire`, `PhoneSaltStore.liveRecord`, `AuthStore.SignOutOtherDevices` and `OperatorStore.Disable` — three of them ordinary reads, and `credential.disabled_at` had 5 live rows, so `Disable` was broken in production. **Why nothing caught it**: every test here runs on SQLite, which compares across types without complaint, and on tables `spec.Migrate` created, where the column really *is* text. Both conditions have to be wrong at once for the bug to show, and no test in the repo makes either one wrong. `unsetText` and `liveDeviceClause` are deleted; the four sites call `st.Unset(role, field)` (`specstore`, cached per column) and `Provision` passes `spec.UnsetClause` into `provisionStatements`, while `ProvisionStatements` — what `cmd/ddl` prints, with no database to ask — keeps using the declared type, which is right for the fresh-database DDL it is printing. **Guards**: `adopted_column_types_test.go` seeds the legacy `auth_phone_salt` table with SQLite `timestamp` columns, runs the real `Provision`, and asserts the emitted one-live index carries no `= ''` and that a live salt is still reachable and retirable through the store — mutation-checked by forcing `spec.UnsetSQL` to the textual form, which turns it red on the index assertion. ### Discrepancies found against the gateway source during porting

- **`registerDevice`'s member-minting branch is gateway-only in a way the
  spec's exclusion list undersold slightly**: it composes not just
  `member.Repository.Create` but also `d.optionalCaller` (the gateway's own
  session-verification helper) to decide whether a caller-supplied
  `member_id` is legitimate. Confirms the exclusion (still correctly
  excluded), just noting the *session* dependency alongside the *member*
  dependency for whoever does the DEV-1656 cutover.
- **`getVerification`'s exclusion and the package-layout hint for
  `VerificationRoutes` read as contradictory on a first pass** — the layout
  note says "the plain Get/Set only," which could be misread as two HTTP
  routes (GET and PUT). Resolved by reading "Get" as the repository method
  `SetVerification`'s read-modify-write calls internally (to carry
  `FullName`/`Phone`/`WorkflowID` forward), not as its own HTTP route — the
  named exclusion for `getVerification` (gated by `requireContactRead`) is
  the one that actually governs the HTTP surface, and only one verification
  route (`PUT .../verification`) was built. Flagging this for whoever
  reads the spec next, since the two sentences do read as being in tension
  until resolved this way.
- Every other named exclusion (`signOutDevice`, `phoneChallenge`/
  `phoneVerify`, `createOperatorCredential`, `submitVerification`,
  `getOrgSettings`/`getOwnOrgSettings`/`putOrgSettings`) matched the actual
  gateway source exactly as described — no further entanglement or
  simplification found beyond what was already documented.
